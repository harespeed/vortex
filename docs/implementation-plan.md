# Vortex Kernel 实施方案（v0.1 → v1.0）

> 状态：实施计划。**本文件不含代码；编码需另行启动。**  
> 范围：Vortex 只做 kernel。`ext-software` / `ext-os` / `ext-hardware` 在外部仓库。边界见 [scope.md](scope.md)。  
> 假设：1 名开发者、每周 5 人日；C++20、macOS 优先、Linux 次之；零包管理器。

---

## 1. 目标与成功标准

### 1.1 v0.1 的成功标准（最小可用）

一条命令能完成：

1. 创建 run。
2. 调用模型（先 fake，后真实）。
3. 调用工具（echo/文件）。
4. 每步落检查点。
5. `kill -9` 后恢复，不重复副作用。
6. 策略拒绝未授权工具；预算超限暂停。
7. SSE 能看到 step/event。
8. `ext-sim` 通过握手与契约测试。

### 1.2 非目标

- 不实现任何真实设备/系统扩展。
- 不做 UI、语音、手机 App。
- 不做多租户、计费、K8s。
- 不把 PQC 作为 v0.1 的阻塞项；TLS 可用经典算法，PQC 在 v0.2+ 接入。

## 4. 每阶段的验收清单

### M0 基础

- [ ] 干净机器按 [howto.md](howto.md) 构建成功。
- [ ] `otool -L`/`ldd` 只显示系统库（OpenSSL/SQLite 静态）。
- [ ] `vortexd --version` 输出版本与构建哈希。
- [ ] SQLite 打开、迁移、`PRAGMA integrity_check` 通过。
- [ ] 日志结构化（JSON 行），级别可配。

### M1 单 run

- [ ] `POST /v1/runs` 返回 run id。
- [ ] fake model 产出一次工具调用，echo 工具返回结果。
- [ ] `GET /v1/runs/{id}/events` 收到 step 事件。
- [ ] 未知路由/超长请求/坏 JSON 返回明确错误。
- [ ] 无认证请求被拒绝。

### M2 持久化

- [ ] 每步后 `steps` 与 `events` 落库。
- [ ] `kill -9` 后重启，从最后 `ok` step 继续。
- [ ] 同一幂等键重复执行不产生重复副作用。
- [ ] 取消后不再发起新工具调用。

### M3 策略

- [ ] 未授权工具被拒绝，返回结构化原因。
- [ ] 不可逆操作进入 `waiting_approval`；批准后执行。
- [ ] 拒绝/超时进入安全状态。
- [ ] 预算超限暂停，不静默降级。

### M4 扩展监督

- [ ] `ext-sim` 独立进程启动、握手、注册能力。
- [ ] 版本不匹配/未签名被拒绝。
- [ ] 心跳超时进入 degraded；连续失败隔离。
- [ ] `ext-sim` 崩溃，内核继续服务其他 run。
- [ ] 命令带幂等键；取消在 100 ms 内生效。

### M5 v0.1

- [ ] 第 1.1 节 8 条全过。
- [ ] 20 个单元测试、5 个集成测试、3 个故障测试通过。
- [ ] 文档：构建、运行、故障排查、限制。
- [ ] 已知问题清单（不隐藏）。

### M6 v0.2

- [ ] 端口 schema 有版本号与错误模型。
- [ ] conformance suite 可由第三方扩展运行。
- [ ] 2 个独立实现（`ext-sim` + 测试 mock）通过。
- [ ] 兼容策略：当前 + 上一个 major。

### M7 v0.3

- [ ] `WorldSnapshot` 由仿真生成，含时间/单位/置信度。
- [ ] 指代消解：唯一/歧义/缺失三态。
- [ ] 接地校验：越界/不可达/未授权三类拒绝。
- [ ] 仿真中完成一次“看→指→抓→放”。

### M8 v1.0

- [ ] 端口冻结；弃用策略与迁移文档。
- [ ] 安全评审：扩展隔离、权限、审计、E-stop 独立性（硬件侧接口）。
- [ ] 性能基线：API p95、恢复时间、内存。
- [ ] 2+ 实现、6 个月使用记录。

## 6. CI 与质量门

- 构建矩阵：macOS arm64、Linux x86_64；Release + Debug。
- Debug：ASan + UBSan。
- 每次提交：单元 + 契约 + 集成。
- 每日：故障注入 + fuzz 短跑。
- 每周：fuzz 长跑、性能基线。
- 质量门：测试失败、端口 schema 破坏、未签名固件/扩展 → 阻止合并。
- 构建可复现：固定编译器/CMake 版本、`SOURCE_DATE_EPOCH`、记录构建清单。

## 7. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| C++ HTTP/JSON 解析漏洞 | 高 | 高 | 严格限制 + fuzz + 最小实现 |
| 范围蔓延到设备扩展 | 高 | 高 | [scope.md](scope.md) 门禁；PR 直接拒绝 |
| 端口过度抽象 | 高 | 中 | 2+ 实现才冻结；v0.1 只 4 个端口 |
| OpenSSL 构建复杂 | 中 | 中 | 固定脚本 + 缓存 + 校验哈希 |
| macOS 沙箱限制 | 中 | 中 | 独立用户 + 路径校验；不依赖 `sandbox-exec` |
| 单人体力/时间 | 高 | 高 | v0.1 砍到 4 端口；每周复盘 |
| 扩展协议反复 | 中 | 高 | v0.2 先冻结握手/错误/取消 |
| PQC 拖慢进度 | 低 | 中 | PQC 不阻塞 v0.1；v0.2+ 接入 |
| 安全事件 | 低 | 高 | 无动态库、最小权限、审计、签名 |
| 性能不达标 | 低 | 低 | I/O-bound；先测再优化 |

## 11. 并行与节奏

- 单人：一次只推进 1 个主工作流 + 1 个测试工作流。
- 每周：一次 demo、一次风险复盘、一次文档更新。
- 每两周：一次“删代码”审查——删掉未使用的抽象与端口。
- 不设“以后再说”的 TODO；要么进计划，要么删。

## 13. 不做什么

- ❌ 不做设备/系统扩展。
- ❌ 不做 UI/语音/手机 App。
- ❌ 不做多租户/计费/云平台。
- ❌ 不把 PQC 作为 v0.1 阻塞项。
- ❌ 不提前冻结 8 个端口。
- ❌ 不为“未来设备”预写分支。

**结论**：先交付一个能跑、能恢复、能拒绝、能扩展的 kernel v0.1；再用契约测试与 `ext-sim` 证明边界；最后才冻结端口。设备扩展是外部项目，不是本仓库的任务。
